# HOMEBASE threat model

What HOMEBASE protects, from whom, what the code does about each threat, which test proves it, and what is left.
Written against commit `29de448` (see [`ARCHITECTURE.md`](ARCHITECTURE.md)). "Tested" means an automated test
in this repository. The unit and integration tests (`npx vitest run`: 29 files, 430 tests, passing at `29de448`)
run on PGlite (Postgres in WebAssembly) through the app's own request handler, over plain `http`; CI repeats the
server tests on PostgreSQL 16. The Playwright tests in `e2e/` drive the built app in Chromium on a local server.
Nothing here has been tested on a real hosted deployment, a hosted Postgres (Supabase or Neon), a real phone or
the wall display.

## What is protected

| Asset | Where it lives |
| --- | --- |
| Children's nicknames, avatars, age bands and what they did (missions, routines, Academy totals, look-back) | `profiles`, `task_occurrences`, `routine_runs`, `routine_step_events`, `academy_sessions`, `events`, `weekly_totals` |
| The household's lists, notes, links, calendar labels, milestones and photos | `shopping_*`, `calendar_*`, `milestones`, `media_blobs` (photo bytes in Postgres) |
| Grown-ups' credentials | `users.password_hash` (scrypt), `memberships.pin_hash` (scrypt, peppered), hashed session/Shortcut/code tokens |
| The integrity of the star ledger | `ledger` (append-only), `wallets` |
| The household's location | `households.settings.location`, rounded to 2 decimal places (about a kilometre) |

## Who might threaten it

- **A curious child at the wall** — can tap anything, may watch a parent type a PIN.
- **A visitor** in the house — can use the wall, see the screen.
- **Someone who finds a public deployment or preview URL.**
- **Another household on the same deployment** — only possible when `HOMEBASE_OPEN_SIGNUP=1`.
- **A lost or stolen phone or tablet.**
- **A malicious web page** open in a grown-up's browser.
- **A hostile string** pasted into a list, a name or a note.
- **A leaked Siri / Shortcuts key.**
- **A compromised dependency** or build tool.
- **Whoever administers the database or the hosting account** (a trust assumption, not a defended-against party).

## Trust boundaries

1. **Browser ↔ API.** Everything a browser sends is untrusted. The server decides access from the session cookie
   alone (`accessOf` in `server/auth/sessions.ts`), never from what the screen says about itself.
2. **Household work ↔ system work.** Household requests run in `inHousehold` as the restricted role
   `homebase_app` with `app.household_id` set; sign-in, sessions, pairing and sweeps run as the owner role
   (`asSystem`). See `server/db/client.ts`, `server/db/migrations/0001_security.sql`.
3. **API ↔ outside services.** Two things leave the server: the weather fetch (`server/weather/providers.ts`)
   and, if a parent has switched it on, the AI helper's calls to one model provider (`server/ai/provider.ts`, row
   25). The Academy is reached only by the wall navigating away.
4. **Wall locked ↔ unlocked.** A wall acts as a child (or `household`) until a grown-up's PIN unlocks it, then as
   that grown-up until a server-side time.

## Things not done (plainly)

- **No second factor** for grown-ups. Passwords plus recovery codes only.
- **No end-to-end encryption.** Everything — nicknames, lists, photos (as `bytea`), e-mail addresses — is plain in
  Postgres. **Whoever administers the database or the hosting account can read all of it**, and can read logs that
  may contain household data after an error (row 17).
- **No encryption of the device cache.** The wall's and phones' IndexedDB hold the last snapshot and the outbox in
  clear (`src/sync/cache.ts`). The brief asked for "encrypted storage when feasible"; it is not done. A key kept
  on the same device beside the data would add little against someone holding the device, and a key held by the
  server would stop a wall from starting up with no signal, which is what the cache is for.
- **PIN is four to eight digits.** Its strength is the rate limit and, if set, the secret-key pepper.
- **No CSRF token**, no per-session device binding, no session list per user.
- **Client sync store**: covered end to end by the Playwright tests and, at store level, by
  `tests/server/store.test.ts` (offline queue through a reload, a lost answer, a refusal, the cache wipe on a
  `401`, demo re-entry). The optimistic reducers have no tests of their own.
- **No dependency auditing** (`npm audit`, update bot) in CI.
- **Concurrency** is tested on PGlite by default and on PostgreSQL only in CI.
- **Nothing has been checked on a real Vercel deployment, Supabase/Neon database, iPhone or the wall display.**
- **Calendar feeds are not built**, so their threats (feed URLs, stored secrets) are not analysed here.
